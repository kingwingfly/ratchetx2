The E2EE chat's web client, in [Leptos](https://leptos.dev). X3DH and the double ratchet run in the page (the [session](../session) crate, compiled to WebAssembly), and the server, the [Worker](../e2ee_chat_worker), only relays what it cannot read.

- **The vault.** The identity key, the prekeys, the sessions and the chats' histories are kept in IndexedDB, each record sealed with AES-256-GCM under a key derived from a passphrase with Argon2id (19 MiB, 2 passes), with the record's name as associated data. Nothing is recoverable without the passphrase. One tab at a time may open the vault (Web Locks), as two would fork the sessions' ratchets.
- **Chats.** Start one with someone's identity key or invitation link (`#chat=<key>&name=<name>`, with `&server=<server>` if the inviter's is not the page's own); the initial message carries a greeting with your name, the session's first message, so the other side can write back at once. Initial messages are accepted as soon as they arrive, while their prekeys are kept, and show as requests until you accept or delete them. Anyone can send one claiming to be anyone, but only the real sender can have encrypted its greeting, so one whose greeting does not decrypt is dropped, using up nothing. One for a chat you have, as the other side started again, takes over the chat, keeping the old session for messages sent on it, which also settles two chats started at once. Compare a chat's safety number, 60 digits computed as Signal's are, out of band, e.g. in person, to know that neither identity key was swapped.
- **Messages.** Text, and files up to 100 MiB: drop them on the page or attach them. Files up to 1 MiB go in their message, images in the TUI client's format, so both clients read each other's text and images. Larger ones go as attachments, as Signal's do: encrypted in 2 MiB chunks under a key of their own and uploaded, while the message carries their ID and key. Their chunks stay in the browser, both sender's and recipient's, and a recipient fetches them on opening the file; the server keeps them for `RETENTION_DAYS`. The message goes as the upload starts, so a recipient can open the file meanwhile, waiting for each chunk as it comes, and gives up only if none comes for a minute. An upload reads the file a chunk at a time, and shows above the composer how far it got; cancelling it deletes it from the server, so its recipients find it gone. While the server cannot be reached, it waits and goes on; after the page goes, it waits, paused, for the file to be chosen again, and goes on from the last chunk the server has, once the file has the SHA-256 it had as far as it was read. That hash stays in the vault, as the server could check guesses of the file with it, and the check matters: going on with another file would encrypt other data under the same key and nonces. The TUI client saves files and attachments to disk, on demand. Messages go in the order they were sent, however quickly: each waits its turn, the ones before it encrypted and pushed, a file read or an attachment's upload started, so that the ratchet numbers them, and the server queues them, in that order; an upload goes on meanwhile. They wait in an outbox until pushed. While the user is on the page, the server notifies the client over a WebSocket when something arrives for it, and the client fetches it at once, polling only every five minutes in case a notification was missed; while the socket is down, it polls faster after activity and slower while idle, and subscribes again. Once the page has been hidden for 30 seconds, or out of focus for 5 minutes, the user is away: the client closes the socket, which tells the server, and syncs only every 30 minutes, so that the Worker and its Durable Objects scale to nothing; on coming back, it syncs at once and subscribes again. The sync button in the top bar fetches at once; it turns red while the server cannot be reached, and its tooltip tells when it last synced and whether notifications are live.
- **Previews.** Files show in the viewer as what their first bytes say they are, their names and types being only the sender's hints. Images (PNG, JPEG, GIF, WebP, AVIF, BMP, ICO, SVG), video (MP4, QuickTime, WebM, Matroska, Ogg) and audio (MP3, AAC, M4A, Ogg and Opus, FLAC, WAV) show as the browser plays them, scaled down to fit whole, portrait or landscape; audio with its cover, title, artist, album and year, if its tags (ID3, MP4, FLAC or Vorbis comments) have them. An attachment opens in the viewer at once, showing how much of it is decrypted until it shows, and closing the viewer stops fetching it. Markdown renders, with its code highlighted, its Mermaid diagrams drawn and its `$…$` and `$$…$$` maths as MathML, and shows as reveal.js slides on demand: `---` between slides, `--` for one below, `Note:` hiding what follows; the arrow keys go through them, and F shows them full screen, scaled to the screen as reveal.js scales them, or fills the window where the browser has no full screen for pages, as on iPhones. PDFs show a page at a time, each drawn as it scrolls into view. Code is highlighted by tree-sitter, in 39 languages, by the file's name or a code block's language. CSV and TSV show as tables (the first 1,000 rows), JSON pretty-printed, diffs colored, vCards and iCalendar files as cards, and ZIP and tar archives (gzipped too, listed as far as 64 MiB unpacked) as their lists of files; other text shows as it is, up to 5 MB, highlighted up to 1 MB. Office documents do not preview. What shows as text, code, Markdown, diffs, tables, lists of files and cards, can be searched in the viewer, with a regular expression or as written, matching case or not: Ctrl+F (⌘F) finds the search box, Enter and Shift+Enter go through the matches, and Esc clears it. A worker searches, in linear time whatever the pattern, and the matches are marked without changing the page, so one may run across the colors of highlighted code. All of it is Rust: PDF pages, diagrams and highlighting run in web workers, of [e2ee_chat_preview](../e2ee_chat_preview), that the page starts when a preview first needs one, as they are larger than the rest of the page together. What peers send shows without running: Markdown's raw HTML shows as written, its links go only to the web or mail, and its images come only from `data:` URLs, so it fetches nothing that tells its sender when it was read; SVGs, Mermaid's too, show as images from `data:` URLs, where their scripts do not run. Other files only download, and never open in the page's origin, where a script could reach the vault; the page's Content-Security-Policy (`_headers`) only runs its own scripts.

The chat list sits beside the open chat, which shows images inline; on a phone, one shows at a time. Buttons that act on the page are icons, each named in its tooltip; a dialog's buttons are words. With no chat open, the page shows your identity key, an invitation link to share, and recent activity, such as requests and prekeys published.

# Build

```sh
trunk build --release   # into dist/, which the Worker serves
```

trunk also builds the previews' workers, binaries of [e2ee_chat_preview](../e2ee_chat_preview), whose grammars, in C, need clang with its WebAssembly target and `llvm-ar`.
