The E2EE chat's web client, in [Leptos](https://leptos.dev). X3DH and the double ratchet run in the page (the [session](../session) crate, compiled to WebAssembly), and the server, the [Worker](../e2ee_chat_worker), only relays what it cannot read.

- **The vault.** The identity key, the prekeys, the sessions and the chats' histories are kept in IndexedDB, each record sealed with AES-256-GCM under a key derived from a passphrase with Argon2id (19 MiB, 2 passes), with the record's name as associated data. Nothing is recoverable without the passphrase. One tab at a time may open the vault (Web Locks), as two would fork the sessions' ratchets.
- **Chats.** Start one with someone's identity key or invitation link (`#chat=<key>&name=<name>`, with `&server=<server>` if the inviter's is not the page's own); the initial message carries a greeting with your name, the session's first message, so the other side can write back at once. Initial messages are accepted as soon as they arrive, while their prekeys are kept, and show as requests until you accept or delete them. Anyone can send one claiming to be anyone, but only the real sender can have encrypted its greeting, so one whose greeting does not decrypt is dropped, using up nothing. One for a chat you have, as the other side started again, or both started at once, joins it: the old session is kept only to decrypt the messages sent on it, and both sides send on one session, as Signal's clients do; if they keep missing each other, the next message starts a new one. Deleting a chat tells the other side, once the server can be reached, which shows it in the chat, and whose next message starts a new session, so that it comes as a new chat, with the messages it sent that the chat deleted never read, sent again; deleting a request tells its sender nothing. Deleting a chat tells the server nothing: it deletes each message once its recipient saved it, and the rest expires. Subscriptions to notifications, whose time the server checks, go by the server's clock, as the `Date` of its responses tells it, so that they work on a device whose clock is off. Compare a chat's safety number, 60 digits computed as Signal's are, out of band, e.g. in person, to know that neither identity key was swapped.
- **Messages.** Text, and files up to 100 MiB: drop them on the page or attach them. Files up to 1 MiB go in their message, images in the TUI client's format, which the archived TUI client, at the tag `archive/e2ee_chat_client`, still reads. Small media shows in the chat, read as it scrolls into view: images and GIFs as they are, videos and audio with their controls, never playing by themselves; that is, media in its message, which its first bytes tell, and attachments up to 8 MiB that their type or name says are media, fetched then. Anything else, or media its bytes say is not, shows as a file to open. Larger ones go as attachments, as Signal's do: encrypted in 2 MiB chunks under a key of their own and uploaded, while the message carries their ID and key. Their chunks stay in the browser, both sender's and recipient's, and a recipient fetches them on opening the file; the server keeps them for `RETENTION_DAYS`. Video and audio play as they are fetched: a service worker, `media-worker.js`, hands each range a player asks for to the page, which fetches and decrypts the chunk it starts in, and only it, so that playing starts once the first chunk is here, and seeking fetches where it lands; an MP4 whose index comes last plays too, as the player asks for its end first. The keys stay in the page; the service worker only passes the plaintext of a range through, in memory. Its sender sees it downloaded only once all its chunks are here, as downloading it whole from the viewer does. Without service workers, as in some private windows, it is fetched whole before it plays. The server is only for those signed in to it: whatever it refuses for the sign-in, from a new vault's keys on, a dialog asks for the server's password; put off, syncing does not ask again until something is sent. Meanwhile, what was sent before signing in waits, with what was sent after it to that chat, in order, and goes once signed in. A file to go as an attachment takes its place in the chat at once, waiting, and shows above the composer as waiting for the sign-in; after the page goes, it waits for the file to be chosen again too. What is held so shows a cross beside its time, which cancels it: it fails, and what waited for it goes. The identity dialog says whether this browser is signed in, until when, and signs out; the cookie of the sign-in is the server's, out of the page's scripts' reach, so the page signs in only to its own server. What expired on the server, as its lifecycle rules deleted it, says so: a message whose content is gone is passed over, and an attachment, or a chunk of it, that is gone is no longer on the server. The message goes as the upload starts, so a recipient can open the file meanwhile, waiting for each chunk as it comes, and gives up only if none comes for a minute. An upload reads the file a chunk at a time, and shows above the composer how far it got, byte by byte; cancelling it deletes it from the server, so its recipients find it gone, and so does deleting its chat before it finished. Its upload token stays in the vault only while it goes. The server keeps attachments for `FILE_RETENTION_DAYS`, however often they are downloaded, and says until when, which the message tells the recipients too; until then, the chat's file browser deletes one from the server sooner, sent or received, with its bin button, pressed twice, as a notice asks, with a token both sides derive from its key: neither side can download it any more, though what each downloaded stays. The history keeps that it did, so the file says it is no longer on the server, and the button does not come back. A recipient who deletes one still uploading stops its upload, whose sender is told, rather than uploading what nobody wants. Its sender opens the file from the file itself, while on the page that chose it, rather than waiting on the server for what is not uploaded yet. While the server cannot be reached, it waits and goes on; after the page goes, it waits, paused, for the file to be chosen again, and goes on from the last chunk the server has, once the file has the SHA-256 it had as far as it was read. That hash stays in the vault, as the server could check guesses of the file with it, and the check matters: going on with another file would encrypt other data under the same key and nonces. Messages go in the order they were sent, however quickly: each waits its turn, the ones before it encrypted and pushed, a file read or an attachment's upload started, so that the ratchet numbers them, and the server queues them, in that order; an upload goes on meanwhile. Both sides show a chat in one order, which the server has no say in: each message carries, encrypted, its Lamport clock, one more than the highest of the chat's so far, either way, and both sides show the chat by clock, then by sender, so that two written at once show alike, and a reply after what it answers, whatever the computers' clocks say. A peer's message never goes before its previous one, nor before one of this side's that it said it read, so a peer cannot slip a message far up the history. A message gets its clock as it goes, after what came so far, and shows last until then. Each shows how far it got, right of its time, as on Telegram: a clock while it waits to be sent, one tick once the server has it, two, as wide as one, once the other side read it, and three once the other side downloaded its attachment whole; the tooltip says it in words. A message is read once it shows with the page on screen; the other side learns of it from events, any number of them in one message, which name messages by their clocks, sent once nothing else waits to go, and never in a request until it is accepted. They are encrypted once, and pushed again as they are until they go, after a reload too, so that retrying, e.g. while the server cannot be reached, uses up no key of the ratchet, of which the other side skips only so many; encrypted on a session that is no longer the one sent on, they are encrypted again on the new one. They wait in an outbox until pushed, unencrypted in the sealed vault, each encrypted just before it goes; with no session to send on, as the two sides kept missing each other or the other deleted the chat, pushing them starts a new one; if the other side has no keys on the server, they fail. When the other side deletes the chat, what it never read goes again, on a new session, which comes to it as a new chat, or on the one it started since, if it started the chat again; with messages to send and no session, the client takes the initial messages first, in case the other side started one; deleting a chat tells the other side first what was read of it. While the user is on the page, the server notifies the client over a WebSocket when something arrives for it, and the client fetches it at once, polling only every five minutes in case a notification was missed; while the socket is down, it polls faster after activity and slower while idle, and subscribes again. Once the page has been hidden for 30 seconds, or out of focus for 5 minutes, the user is away: the client closes the socket, which tells the server, and syncs only every 30 minutes, so that the Worker and its Durable Objects scale to nothing; on coming back, it syncs at once and subscribes again. The sync button in the top bar fetches at once; it turns red while the server cannot be reached, and its tooltip tells when it last synced and whether notifications are live.
- **Files.** Each chat has a file browser, its folder button in the chat's header: the files both sides sent, newest first, by month, on shelves by what they are, which their content tells, as the viewer has it, not only their names: media, documents (PDF, office documents, text, Markdown, tables, contacts and events), code, archives, and the rest; an attachment, whose bytes are not here, by its name and type. Media shows as a grid of previews, read as they scroll into view: images as they are, videos still at their first frames under their length, and audio by its cover, if its tags have one; the rest as a list of names, sizes, days and senders, where media shows its preview too. Media too large to fetch for this, an attachment over 8 MiB, shows a glyph of its sort. Each opens in the viewer.
- **Previews.** Files show in the viewer as what their first bytes say they are, their names and types being only the sender's hints. Images (PNG, JPEG, GIF, WebP, AVIF, BMP, ICO, SVG), video (MP4, QuickTime, WebM, Matroska, Ogg) and audio (MP3, AAC, M4A, Ogg and Opus, FLAC, WAV) show as the browser plays them, scaled down to fit whole, portrait or landscape; audio with its cover, title, artist, album and year, if its tags (ID3, MP4, FLAC or Vorbis comments) have them. An attachment opens in the viewer at once, showing how much of it is decrypted until it shows, and closing the viewer stops fetching it. Markdown renders, with its code highlighted, its Mermaid diagrams drawn and its `$…$` and `$$…$$` maths as MathML, and shows as reveal.js slides on demand: `---` between slides, `--` for one below, `Note:` hiding what follows; the arrow keys go through them, and F shows them full screen, scaled to the screen as reveal.js scales them, or fills the window where the browser has no full screen for pages, as on iPhones. PDFs show a page at a time, each drawn as it scrolls into view. Code is highlighted by tree-sitter, in 39 languages, by the file's name or a code block's language. CSV and TSV show as tables (the first 1,000 rows), JSON pretty-printed, diffs colored, vCards and iCalendar files as cards, and ZIP and tar archives (gzipped too, listed as far as 64 MiB unpacked) as their lists of files; other text shows as it is, up to 5 MB, highlighted up to 1 MB. Office documents do not preview. What shows as text, code, Markdown, diffs, tables, lists of files and cards, can be searched in the viewer, with a regular expression or as written, matching case or not: Ctrl+F (⌘F) finds the search box, Enter and Shift+Enter go through the matches, and Esc clears it. A worker searches, in linear time whatever the pattern, and the matches are marked without changing the page, so one may run across the colors of highlighted code. All of it is Rust: PDF pages, diagrams and highlighting run in web workers, of [e2ee_chat_preview](../e2ee_chat_preview), that the page starts when a preview first needs one, as they are larger than the rest of the page together. What peers send shows without running: Markdown's raw HTML shows as written, its links go only to the web or mail, and its images come only from `data:` URLs, so it fetches nothing that tells its sender when it was read; SVGs, Mermaid's too, show as images from `data:` URLs, where their scripts do not run. Other files only download, and never open in the page's origin, where a script could reach the vault; the page's Content-Security-Policy (`_headers`) only runs its own scripts.

The chat list sits beside the open chat, which shows small media in place, each read from the vault as it scrolls into view, as files are kept apart from the history, so that a long chat opens at once; on a phone, one shows at a time. Buttons that act on the page are icons, each named in its tooltip; a dialog's buttons are words. With no chat open, the page shows your identity key, an invitation link to share, and recent activity, such as requests and prekeys published.

# Build

```sh
trunk build --release   # into dist/, which the Worker serves
```

trunk also builds the previews' workers, binaries of [e2ee_chat_preview](../e2ee_chat_preview), whose grammars, in C, need clang with its WebAssembly target and `llvm-ar`.
