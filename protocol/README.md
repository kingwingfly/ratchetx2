The E2EE chat's wire protocol: the **handshake** service (publish and fetch prekeys, exchange X3DH initial messages) and the **mailbox** service (queues of encrypted messages).

The **attachment** service (`proto/attachment.proto`, module [`attachment`]) carries files too large for a message: their sender encrypts them under a key of their own and uploads them in chunks of at most 2 MiB, and a message gives the recipients the attachment's ID and key, so the server only sees ciphertext. The recipients can download it while it is uploaded, as a chunk not uploaded yet is told from an attachment that is gone. Nothing names who uploaded it or whom it is for, and the recipients may download it as often as they like, until it expires or a peer deletes it. It has two tokens: its upload token, random, which the server gives the uploader alone as the upload starts, uploads its chunks and is no use after; its delete token, which the peers derive from the attachment's key, HKDF-SHA256 with `attachment.v1/delete` as info, deletes it at any time, uploaded or not, so a recipient who does not want it spares the uploader the rest. Starting an upload gives the server only SHA-256 of the delete token and is signed by nobody: holding either token shows only that one knew what every peer of the chat knows. Each chunk is uploaded once: uploading it again keeps the first copy, so the upload token never changes what was downloaded.

The mailbox's pushes and fetches are open, as what they carry is encrypted end to end. A message goes once its recipient has it, as Signal's server deletes a message once delivered: its push gives the server SHA-256 of its **delivery token**, a secret only the two peers can compute, and the recipient gives the token back with a later fetch, once it kept the message. No signature or login is needed, so it proves nothing to anyone else. A message never delivered expires.

**Notifications** (`proto/notify.proto`, module [`notify`]) let a client learn at once that something arrived for it, instead of polling: it subscribes with a request signed by its identity key, and the server tells it the sender of each message and each initial message. They carry nothing secret and are only hints, as what arrived is still fetched with the services; how they travel is up to the server, e.g. the Worker's WebSocket.

The messages are defined in `proto/handshake.proto` and `proto/mailbox.proto` (packages `handshake.v1`, `mailbox.v1`), so other languages can implement either side. So is what the clients' messages carry, encrypted, which the server never sees: `proto/content.proto` (package `content.v1`, module [`content`]), with each message's Lamport clock, which orders the chat alike on both sides and names the message in events, as read or downloaded. A message may carry the initial message of its session, which its sender sends while the recipient has not answered it, as Signal's clients do, so that it can be accepted from there if the one in the inbox was lost. Handshake requests that change or read Bob's data are signed with his identity key, see [signed requests](handshake#signed-requests). The handshake messages convert to and from [x3dh](../x3dh)'s types, checking key and signature lengths. An initial message carries the session's first message, X3DH's initial ciphertext, which only its sender can have encrypted: the recipient drops an initial message whose first message does not decrypt. The server cannot tell, so it keeps the first message as it is, up to a size limit.

The services run over plain HTTP with the [Connect protocol](https://connectrpc.com/docs/protocol), which browsers and Cloudflare Workers can speak, and any Connect client can call. The `.proto` files define the services too, so Connect clients in other languages can be generated from them; the paths here are checked against them. Other transports, such as gRPC with stubs generated from the same files, plug in by implementing the client traits and hosting the servers.

For each service there is a client trait ([`Handshake`](handshake::Handshake), [`Mailbox`](mailbox::Mailbox), each with a `Local` variant whose futures need not be `Send`), and with the `server` feature, the server's logic over the [storage](../storage) traits. A server can also be used directly as a client, in-process.

# Features

- **protox** (default): compile the `.proto` files with [protox](https://crates.io/crates/protox); without it, `protoc` must be installed.
- **serde**, **rkyv**: derive their traits on the message types.
- **server**: the servers' logic (`handshake::HandshakeServer`, `mailbox::MailboxServer`).
- **connect**: Connect clients over any HTTP client, and answering calls inside any HTTP server (module `connect`); no I/O of its own, so it builds for `wasm32-unknown-unknown`.
